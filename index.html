Agente de I.A SDR no WhatsApp Web, com foco em tribunais.

Projeto com Docker + Node.js integrado ao WhatsApp Web onde o usuário pode configurar sua própria I.A – com foco em SDR e suporte – e conectar-se a endpoints que podem ser integrados a outros sistemas gratuitamente.

Contexto da entrega

A entrega principal é configurar um agente de I.A para suporte e onboarding via WhatsApp de um tribunal fictício, permitindo:

  • Pré-atendimento de cidadãos (FAQ, orientações iniciais).
  • Triagem de demandas, com indicação de canal/processo adequado.
  • Integração futura com sistemas internos via endpoints HTTP.

🎯 Objetivo de Negócio

Reduzir o tempo e o esforço de atendimento inicial (onboarding e dúvidas frequentes) de cidadãos/usuários de um tribunal, oferecendo um pré-atendimento inteligente via WhatsApp, com possibilidade de takeover humano e integração com outros sistemas.

Metas principais

  • Diminuir a carga de trabalho repetitiva da equipe humana.
  • Aumentar a agilidade e padronização das respostas de primeiro nível.
  • Centralizar registros de conversas em MongoDB para análise posterior.
  • Facilitar integrações com sistemas legados via endpoints HTTP simples.

Indicadores de sucesso (KPIs)

  • Redução do tempo médio da primeira resposta no WhatsApp.
  • Percentual de dúvidas resolvidas diretamente pelo agente de I.A.
  • Redução do volume de atendimentos humanos para demandas simples.
  • Número de integrações ativas com sistemas do tribunal (via endpoints).

🧪 Como está HOJE x Próxima Entrega

A base técnica está pronta: WhatsApp Web + Node + OpenAI + MongoDB. Hoje o protótipo funciona com prompts e configurações fixas; a entrega final leva o projeto ao nível especialista, com configuração dinâmica da I.A via painel, deixando no .env apenas a string de conexão do Mongo.

Protótipo fixo Versão atual do repositório

Arquitetura e fluxo atual

  • Backend Node.js + Express rodando via Docker Compose.
  • Conexão com WhatsApp via whatsapp-web.js (LocalAuth + QR Code).
  • Todas as mensagens são normalizadas e armazenadas em MongoDB na coleção messages, com uso de índices e TTL configurável (MSG_TTL_DAYS).
  • Áudios são transcritos localmente (transcribeAudioLocal) antes de ir para a I.A.
  • A I.A é chamada via OpenAI Chat Completions, com JSON Schema fixo retornando campos como intencao e ia_reply_messages.
Prompts engessados

Configuração da I.A hoje

  • Persona, contexto, regras e catálogo estão em src/prompts.js, escritos diretamente no código.
  • Variáveis sensíveis e de comportamento são definidas em .env/.env.example, como: OPENAI_API_KEY, OPENAI_CHAT_MODEL, IA_CONTEXT_MAX_MINUTES, HUMAN_HOLD_MS, MSG_TTL_DAYS, DASH_TOKEN, entre outras.
  • Alterar persona, contexto ou regras exige modificar arquivos de código e recriar a imagem Docker.
  • O foco atual é comprovar o fluxo técnico de ponta a ponta, não a auto-configuração ainda.
Painel em tempo real

Painel + logs (projeto atual)

  • SPA em Quasar + Vue 3 consumindo dados via SSE em GET /events.
  • O painel recebe: QR Code da sessão, logs em tempo real e status dos chats (IA ON/OFF, cooldown humano, título do chat).
  • A sessão do WhatsApp pode ser reiniciada manualmente via endpoint POST /reset-session.
  • Existe um endpoint HTTP simples para envio de texto (POST /send-text) usado por integrações e pela própria SPA.
Limitações atuais

O que ainda não é dinâmico?

  • Cadastro/alteração da persona da I.A é feito diretamente no código.
  • Parâmetros como IA_CONTEXT_MAX_MINUTES e HUMAN_HOLD_MS são alterados via .env e exigem restart do container.
  • Não há ainda uma tela de configuração persistente para catálogo de produtos/serviços ou regras avançadas.
  • Configuração ainda é pensada para um único “cliente” (uma empresa/tribunal) por vez, com pouca multi-tenantização.
Nível especialista TO-BE (entrega esperada)

I.A auto-configurável via painel

  • Criar telas no painel (Quasar + Vue 3) para configurar dinamicamente:
    • Chave da OpenAI (OPENAI_API_KEY).
    • Modelo de chat (OPENAI_CHAT_MODEL).
    • Tempo de contexto da conversa (IA_CONTEXT_MAX_MINUTES).
    • Cooldown do humano (HUMAN_HOLD_MS).
    • Persona, contexto, regras e metadados da I.A.
    • Catálogo (título, descrição, imagens, preço, categoria, etc.).
  • Essas configurações passam a ser salvas em MongoDB como documento de configuração, e não mais em arquivos .js ou .env.
  • O backend passa a ler as configurações em runtime, permitindo ajustes sem rebuild de container.
.env minimalista

Somente Mongo no .env

  • No resultado final, a única informação crítica a ser configurada manualmente no .env será: a string de conexão do MongoDB (MONGODB_URI).
  • Demais parâmetros (I.A, catálogo, timeouts, token do painel, etc.) serão: dinâmicos (via painel) ou fixos em código com valores seguros.
  • Isso facilita instalar o sistema em máquinas de clientes sem conhecimento técnico profundo (basta informar o Mongo).
  • Abre caminho para múltiplos “perfis de configuração” no futuro (ex.: vários tribunais/órgãos usando o mesmo core).
Fluxo enxuto (TO-BE)

Processo alvo de atendimento

  • Cidadão envia mensagem/áudio para o WhatsApp do tribunal fictício.
  • Iano normaliza, transcreve (se áudio) e registra a mensagem em Mongo.
  • I.A lê contexto recente + regras configuradas pelo painel e responde.
  • Em cenários fora de escopo, o bot orienta o canal correto (balcão, sistema processual, telefone, etc.).
  • Logs e métricas podem ser usados para melhorar continuamente o fluxo e treinar a equipe.

🚀 Como rodar o Iano Whatsapp (Docker local)

Abaixo um fluxo resumido baseado no projeto atual. O foco da residência é permitir que futuros usuários precisem configurar apenas o Mongo; contudo, na versão atual ainda existem outras variáveis em .env.

1 Clonar o repositório

Repositório oficial do código fonte:

git clone https://github.com/samuelvictorol/iano-whatsapp.git
cd iano-whatsapp

Opcionalmente, consulte também o board de backlog e kanban:
https://github.com/users/samuelvictorol/projects/6

2 Configurar o .env

Hoje: copie o arquivo .env.example para .env e ajuste as variáveis principais, em especial:

  • MONGODB_URI – string de conexão do MongoDB.
  • MONGO_DB e MONGO_COL (opcional, com defaults).
  • OPENAI_API_KEY e OPENAI_CHAT_MODEL.
  • IA_CONTEXT_MAX_MINUTES e HUMAN_HOLD_MS.
  • DASH_TOKEN para proteger o painel, se desejado.

Futuro (TO-BE): apenas MONGODB_URI continuará sendo configurado manualmente; demais parâmetros serão preenchidos via painel.

3 Subir com Docker Compose

Com o Docker instalado:

docker compose up -d --build

Após subir, o servidor Node (logger) ficará ouvindo na porta definida em PORT (por padrão, 10000).

A SPA em Quasar (frontend) se conecta ao backend via HTTP e ao canal /events (SSE) para logs, status e QR Code.

4 Autenticar o WhatsApp e testar

  • Acesse o painel (ex.: http://localhost:10000 ou porta exposta).
  • Escaneie o QR Code com o app do WhatsApp (aparece no painel).
  • Aguarde a sessão ficar “conectada”.
  • Envie uma mensagem de outro número para o WhatsApp conectado e observe:
    • Registro automático no MongoDB.
    • Respostas da I.A seguindo o prompt atual.
    • Takeover humano se alguém responder manualmente.

📡 Endpoints disponíveis (versão atual)

O backend do Iano Whatsapp expõe alguns endpoints HTTP simples para interação com o WhatsApp e com o painel em tempo real. A seguir, um resumo dos principais endpoints da versão atual do projeto.

/events Server-Sent Events – QR Code, logs e status de chats
GET
›

Endpoint de Server-Sent Events (SSE) usado pelo painel Quasar/Vue para receber atualizações em tempo real:

  • QR Code da sessão (type: "qr").
  • Buffer de logs recentes (type: "logs").
  • Status dos chats (type: "status" e "status_one"), indicando: IA ON/OFF, cooldown humano, títulos, etc.
GET /events
Accept: text/event-stream
/send-text Envia uma mensagem de texto para um chatId via WhatsApp
POST
›

Permite disparar uma mensagem de texto de forma manual ou por outros sistemas integrados, usando o número/log do WhatsApp já conectado.

Se um DASH_TOKEN estiver definido, é necessário enviá-lo no cabeçalho X-Token. 

POST /send-text
X-Token: <DASH_TOKEN opcional>
Content-Type: application/json

{
  "chatId": "5511999999999@c.us",
  "text": "Olá, esta mensagem foi enviada pelo Iano Whatsapp!"
}
/reset-session Reseta a sessão do WhatsApp Web (LocalAuth)
POST
›

Usado para forçar um reset da sessão do WhatsApp (por exemplo, quando o QR Code expira ou a sessão apresenta inconsistências).

Também respeita, se configurado, o cabeçalho X-Token com DASH_TOKEN. 

POST /reset-session
X-Token: <DASH_TOKEN opcional>

🧩 Tecnologias e tópicos da disciplina aplicados

O projeto Iano Whatsapp nasce diretamente dos tópicos trabalhados em sala: uso de prompts para prototipação, geração de código, I.A em fluxo real e desenvolvimento de SPA responsiva.

Tecnologias utilizadas

  • Docker Compose – orquestração do backend e demais serviços.
  • Node.js + Express – servidor HTTP e camada de API.
  • JavaScript (backend e frontend SPA).
  • Quasar Framework + Vue 3 – painel web responsivo e dinâmico.
  • OpenAI API – respostas da I.A e transcrição de áudio (Whisper).
  • whatsapp-web.js – integração com WhatsApp Web via QR Code.
  • MongoDB – armazenamento de mensagens, logs e (futuramente) configurações.

Tópicos da matéria utilizados

  • Geração de protótipo inicial a partir de prompts, incluindo a arquitetura inspirada em outro protótipo (WhatsApp Logger) também produzido com GPT.
  • Geração de endpoints e lógica de negócio em Node.js via prompts bem definidos.
  • Criação de telas SPA responsivas (Quasar + Vue 3) para painel, logs e QR Code.
  • Conceitos de fluxo enxuto (TO-BE), robustez, controle e sustentabilidade aplicados a um caso de uso de tribunal fictício.
